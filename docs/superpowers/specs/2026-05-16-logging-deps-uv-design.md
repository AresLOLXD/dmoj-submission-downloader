# Design: Logging System, Dependency Updates, and uv Migration

**Date:** 2026-05-16  
**Project:** dmoj-downloader  
**Scope:** Three coordinated improvements — structured logging, dependency upgrades, uv as package manager

---

## 1. Logging System

### Architecture

A single `app/logging_config.py` module configures Python's stdlib `logging` once at app startup. No external libraries required. Every module calls `logging.getLogger(__name__)` — the pattern `dmoj_client.py` already uses.

### Configuration

`app/config.py` exposes:
```python
LOG_LEVEL: str = os.environ.get("LOG_LEVEL", "INFO").upper()
```

`.env.example` adds:
```
LOG_LEVEL=INFO
```

`app/logging_config.py`:
```python
import logging

def configure_logging(level: str) -> None:
    logging.basicConfig(
        level=level,
        format="%(levelname)-8s %(asctime)s %(name)s - %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )
```

`app/main.py` calls `configure_logging(config.LOG_LEVEL)` before the app is created.

### Events Per Module

**`app/main.py`**
- `INFO` — download started: `slug=X user=Y`
- `INFO` — download done: `slug=X submissions=N duration=Xs`
- `WARNING` — invalid slug: `slug=X user=Y`
- `WARNING` — contest not found: `slug=X user=Y`

A lightweight middleware logs HTTP method, path, status code, and duration for every request:
```
INFO     2026-05-16 12:00:01 app.main - GET /download slug=contest2024 status=200 duration=3.21s
```

**`app/auth.py`**
- `INFO` — login success: `user=X`
- `WARNING` — login failed: `user=X`
- `INFO` — logout: `user=X`

**`app/admin.py`**
- `INFO` — user created: `admin=X username=Y`
- `INFO` — user toggled: `admin=X target=Y active=True/False`
- `INFO` — password reset: `admin=X target=Y`

**`app/dmoj_client.py`**
- Already has `WARNING` on fetch failure — no changes needed.

### Error Handling

Uncaught exceptions propagate normally through FastAPI's exception handling. The logging system does not swallow errors — it only adds observability at known decision points.

**Strategy:** Update `pyproject.toml` (created in section 3), run `uv sync`, run `pytest`, fix any failures.

## 3. uv Migration

### What Changes

`requirements.txt` is replaced by `pyproject.toml` as the source of truth. `uv.lock` provides a reproducible lockfile. The existing `.venv` is reused by uv if present.

### File Changes

| File | Action |
|---|---|
| `pyproject.toml` | Create — runtime deps + dev deps |
| `uv.lock` | Create — generated by `uv sync` |
| `requirements.txt` | Delete |
| `README.md` | Update setup instructions |
| `.gitignore` | Verify `.venv` is excluded |

### `pyproject.toml` Structure

```toml
[project]
name = "dmoj-downloader"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "fastapi[standard]>=0.136.1",
    "uvicorn[standard]>=0.47.0",
    "jinja2>=3.1",
    "httpx>=0.28.1",
    "aiosqlite>=0.20.0",
    "bcrypt>=5.0.0",
    "itsdangerous>=2.2.0",
    "zipstream-new>=1.1.8",
    "python-multipart>=0.0.9",
    "python-dotenv>=1.0.1",
]

[dependency-groups]
dev = [
    "pytest>=9.0.3",
    "pytest-asyncio>=1.3.0",
    "respx>=0.21.1",
]
```

### Developer Workflow After Migration

```bash
# Setup
uv sync

# Run app
uv run uvicorn app.main:app --reload

# Run tests
uv run pytest
```

The `.service` file for systemd uses the full venv path (`/path/to/.venv/bin/uvicorn`) — no changes needed there since uv creates the same `.venv` structure.

## Subagents

| Task | Subagent | Reason |
|---|---|---|
| Logging system (`logging_config.py`, middleware, per-module loggers) | `voltagent-lang:fastapi-developer` | FastAPI middleware patterns, async request lifecycle, stdlib logging wiring |
| Dependency updates (bump versions, fix breaking changes) | `voltagent-dev-exp:dependency-manager` | Specialized in auditing versions, resolving conflicts, validating upgrades |
| uv migration (`pyproject.toml`, delete `requirements.txt`, update docs) | `voltagent-dev-exp:dependency-manager` | uv/pyproject.toml expertise fits naturally with the dependency-manager role |

These three tasks are independent and can be dispatched in parallel once the implementation plan is ready.

## Testing

- All existing tests must pass after each change.
- Logging events are verified by checking that loggers are called — no new test files needed unless a log path is complex enough to warrant it.
- Dependency updates are validated by the existing test suite passing cleanly.

## Out of Scope

- Log rotation or file output (journald captures stdout from the systemd service).
- Centralized log aggregation (Loki, ELK, etc.).
- Structured JSON logging.
- Any new application features.
